# 요청 밖의 일은 허락을 받고 진행하기

bin은 자기가 시킨 일만 반영되기를 원합니다. 요청 범위를 넘는 변경은 아무리 좋은 의도여도 bin이 검토하지 않은 결과물이 게임과 패치노트에 섞이게 만들고, 무엇이 자기 결정이었는지 흐려지게 합니다. 그래서 요청 밖의 일은 **하기 전에** 묻고, 답을 받은 뒤에만 진행합니다.

## 실제로 있었던 일

bin은 미국 고교 밸런스 방향으로 "1번(그대로 둔다)"만 골랐습니다. 그런데 Claude가 선수 만들기 화면의 학교 탭에 난이도 차이 안내 문구 2개를 덧붙였습니다. bin이 고른 1번 선택지 설명에 "안내합니다"가 한 줄 섞여 있었다는 이유였지만, bin은 그것까지 허락한 것으로 생각하지 않았습니다. 이런 일이 다시 없게 하는 것이 이 스킬의 목적입니다.

## 무엇이 "요청 밖의 일"인가

요청 문장에 직접 나오지 않고, 요청을 동작하게 하는 데 꼭 필요하지도 않은 변경입니다. 예를 들면:

- 게임 안 안내 문구, 버튼, 화면 요소 추가나 수정
- 밸런스 수치 조정 (시뮬레이션 결과가 마음에 들지 않아도 먼저 묻기)
- 요청과 상관없는 리팩터링, 이름 변경, 파일 이동, 삭제
- 새 기능, 새 설정 옵션, 새 분석 이벤트
- 요청받지 않은 문서·README 내용 추가 (아래 "묻지 않아도 되는 것"의 절차는 제외)

## 묻지 않아도 되는 것

- 요청을 동작하게 하는 데 꼭 필요한 수정: 타입 오류 해결, 바뀐 데이터 개수에 맞춘 테스트 숫자, 새 리그를 넣었을 때 빠진 표 항목 채우기
- CLAUDE.md가 정한 절차: 버전과 패치노트 갱신, 테스트 추가, 세이브 변환(saveMigration), 마이그레이션 실행 안내

이런 것도 작업이 끝난 뒤 보고에 무엇을 왜 했는지 적습니다.

애매하면 묻습니다. 묻는 비용은 작고, 허락 없이 넣은 변경을 되돌리는 비용은 큽니다.

## 묻는 방법

1. 요청받은 일은 그대로 진행합니다. 요청 밖의 아이디어 때문에 요청받은 일을 멈추지 않습니다.
2. 요청 밖의 변경은 **하지 않은 상태로** AskUserQuestion으로 묻습니다. 무엇을, 왜, 어떤 영향이 있는지 한두 문장으로 적고, "하기 / 하지 않기"나 구체적인 안을 선택지로 줍니다.
3. 여러 개라면 한 번에 모아서 묻습니다 (질문은 최대 4개).
4. 거절되면 하지 않고, 같은 제안을 다시 하지 않습니다.

## 선택지를 제안할 때

bin에게 방향을 고르게 할 때 어떤 선택지에 요청 밖의 작업이 딸려 있다면, 그 부분을 설명에 따로 분명히 적습니다. 본래 선택과 섞어 쓰지 않습니다.

- 나쁜 예: "그대로 둔다: 미국 고교를 엘리트 루트로 둡니다. 대신 선택 화면에 난이도 차이를 안내합니다."
- 좋은 예: "그대로 둔다: 수치를 바꾸지 않습니다." 그리고 별도 질문으로 "선택 화면에 난이도 차이 안내 문구를 추가할까요?"

이렇게 해야 bin이 무엇을 골랐는지가 분명해집니다.

## 보고할 때

마지막 보고에는 요청받은 것, 필요해서 함께 한 것(이유 포함), 제안만 하고 하지 않은 것을 구분해 적습니다.
